# ADR-0009 QMS Engineering Data Module Boundary

## Status

Accepted

## Context

The Jinheng QMS phase-one design starts with a tightly coupled engineering-data chain:
Part, Drawing, and DrawingRevision. The source design proposes several fine-grained QMS
modules, while IAF requires a modular monolith and explicitly avoids premature service
decomposition.

Splitting Part and DrawingRevision into separate Maven modules now would introduce a
cross-module lookup on every drawing command before the business boundaries and load
profile have been validated.

## Decision

Add one flat Maven module, `iaf-qms-engineering`, for the first engineering-data
vertical slice. It owns:

- `qms_part`
- `qms_drawing`
- `qms_drawing_revision`
- the QMS audit records generated by this module

The module follows `interfaces/application/domain/infrastructure` and depends only on
IAF shared/platform contracts. `iaf-app` assembles it into the single deployment unit.

The HTTP namespace follows the higher-priority IAF rule:
`/api/qms/{resources}`. It intentionally does not use the source design's unscoped
`/api/v1/{resources}` prefix.

Later capabilities may be introduced as cohesive modules such as QMS inspection,
validation, and AI gateway modules. A new ADR is required before splitting the
engineering module or moving table ownership.

## Consequences

- Phase-one Part/Drawing/Revision invariants can be enforced in one transaction and
  repository boundary.
- The first delivery adds one module instead of mirroring every future bounded context.
- Any later service extraction must replace direct relational ownership with published
  APIs/events and read models.
