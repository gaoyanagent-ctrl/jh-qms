# IAF 平台 AI 开发总体策略

## 1. 定位

IAF 平台本身也必须采用 AI Coding 方式开发，但不能让 AI 直接从自然语言随意改代码。推荐采用“人类架构决策 + AI 结构化开发 + 自动化质量门禁”的模式。

IAF 的 AI 开发不是普通辅助编程，而是一个工程化流程：

```text
业务/架构意图
  -> 结构化需求说明
  -> DSL/数据模型/接口契约
  -> Codex 执行计划
  -> 代码变更
  -> 自动化测试
  -> 质量门禁
  -> 人工评审
  -> 合并主干
```

## 2. 基本原则

1. AI 不直接决定架构边界。架构、模块划分、数据一致性、权限模型、审批模型、状态机模型由人确认。
2. AI 可以生成和修改代码，但必须遵守仓库级规则、模块级规则、测试规则和质量门禁。
3. 每个开发任务必须有任务说明、影响范围、验收标准和测试要求。
4. 所有业务单据、状态机、审批流、权限点、规则配置必须优先修改 DSL/契约，再修改实现代码。
5. 不允许 AI 绕过权限、事务、审计、数据权限、租户字段、多组织字段等平台约束。
6. 代码生成后必须可以被人类开发者理解、修改和维护。

## 3. AI 参与边界

| 工作类型 | AI 可做 | 人必须确认 |
|---|---|---|
| 需求整理 | 将自然语言转为任务说明、字段清单、状态流转 | 业务边界、优先级、异常场景 |
| 架构设计 | 给出候选方案、影响分析 | 技术路线、模块边界、数据一致性方案 |
| 代码生成 | CRUD、接口、页面、测试、migration | 复杂领域逻辑、核心事务、权限策略 |
| 重构 | 小范围重构、重复代码收敛 | 跨模块重构、公共模型变化 |
| 测试 | 单元测试、集成测试、E2E 用例草案 | 关键验收场景、真实业务数据 |
| 评审 | 静态检查、diff 总结、风险提示 | 合并决策、架构例外审批 |

## 4. 推荐 AI 工具角色

- Codex CLI：执行明确的开发任务、修改仓库代码、运行测试、修复失败。
- Cursor：日常编辑、局部代码理解、前后端联调。
- Claude Code：复杂重构、长上下文代码审查、架构一致性检查。

三类工具都必须读取仓库内的 `AGENTS.md`、`ai-coding/rules/*`、`docs/architecture/*` 和当前任务文件。
